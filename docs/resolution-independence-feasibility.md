# Apex Controller Lab：分辨率与环境无关性可行性分析

> 文档版本：0.1
> 日期：2026-07-31
> 状态：分析稿，未实施，未在任何云环境实测
> 适用范围：`windows/` 下的截图门控运行器
> 相关文档：[技术可行性](apex-ui-drop-screenshot-feasibility.md)、[可恢复任务运行器设计](resilient-task-runner-design.md)、[能力证据矩阵](capability-evidence.md)

## 1. 结论

| 问题 | 结论 | 关键前提 |
|---|---|---|
| 云 Windows 上第一个坏的是分辨率吗 | **不是**，是采集 | DXGI 桌面复制在纯 RDP 会话下不可用；分辨率校验根本走不到 |
| 支持 16:9 家族（1080p / 1440p / 4K） | 可行，代价小 | 加一层可逆的画布变换，配置零迁移 |
| 支持任意宽高比（21:9 等） | 可行，但必须换定位范式 | 游戏 UI 自身布局法则改变，任何比例换算都会静默算错 |
| 完全环境无关 | **不值得追求** | 键位绑定、界面语言、赛季 UI 版本仍是独立变量，分辨率只是其中一维 |

核心判断：**当前的病根不是"写死了 2560×1440"，而是"坐标没有坐标系"。** `[610, 150]` 这个字面量不说明自己活在屏幕空间、窗口空间还是某个参考画布里。一旦数字脱离坐标系到处传递，任何环境变化都会静默算错——而不是报错。把分辨率写进文件名只是给这个缺陷加了个标签，没有修它。

同时要明确一个反直觉的结论：**通用性最高的手段不是更聪明的坐标换算，而是尽量不用坐标。** 这与 [§9.4 既有决定](resilient-task-runner-design.md)（消除动作优先键盘）是同一个方向，本文主张把它扩大适用，而不是推翻它。

## 2. 现状盘点

以下均以代码为准，非推测。

### 2.1 硬耦合点

| 位置 | 性质 | 说明 |
|---|---|---|
| `windows/apex_automation/vision.py:105-108` | 硬校验 | 捕获分辨率与配置 `environment.width/height` 不完全相等即抛 `ValueError` |
| `windows/config/enter-game.zh-CN.json:14` 等 | 绝对坐标表 | 12 个点击目标写成 `[610, 150]` 形式的屏幕像素 |
| `windows/config/play-overlays.zh-CN.json:7-10` | 绝对矩形 | OCR 区域写成 `[1360, 760, 2560, 1440]` |
| `windows/apex_automation/vision.py:95-100` | 像素等尺寸 | 模板尺寸必须与 ROI 宽高逐像素相等，否则拒绝装载 |
| `windows/apex_automation/progression.py:13-20` | **硬编码且不可覆盖** | 等级/经验 ROI 是模块常量；`cli.py:605` 构造时只传 `min_confidence`，配置无法覆盖 |

前四项换分辨率时可以靠新建配置解决；**第五项必须改代码**，是唯一一个配置层修不掉的。

### 2.2 命名误导

`enter-game.zh-CN.json`、`game-states.zh-CN.json`、`play-overlays.zh-CN.json`、`obstacle-rules.zh-CN.json` 文件名不含分辨率，内容却是 2560×1440 绝对坐标。它们看起来像通用配置，实际不是。做多环境支持时这是最容易踩的一脚。

### 2.3 已经不耦合的部分

不是全盘皆输，有两块已经站在正确的一侧：

- `input_win32.py:160-163`：点击已按 `screen_width/height` 归一化到 0..65535，**执行层本来就不依赖 2K**。
- `ocr_obstacles.py:27-33`：`OcrToken` 已带 `roi` 字段，注释写明"provider 读整帧时是绝对坐标"。**从识别结果反推位置的管道已经铺好了。**

### 2.4 22 条能力的输入构成

| 类型 | 条数 | 是否依赖坐标 |
|---|---|---|
| `key` | 9 | 否 |
| `sequence` | 1 | 否 |
| `click` | 12 | **是** |

也就是说 [§9.4 的"优先键盘"](resilient-task-runner-design.md) 已经覆盖了 10/22，剩下 12 条点击正是全部脆弱性所在。这个比例本身就说明键盘优先是有效的，只是没走完。

## 3. 云 Windows 的真实故障顺序

[技术可行性文档 §12 阶段 C](apex-ui-drop-screenshot-feasibility.md) 已把云兼容性列为闸门。本文补充**失败会按什么顺序发生**，因为这决定了改造的优先级：

1. **采集**（最先坏）。`capture.py` 用 `dxcam` 走 DXGI 桌面复制。RDP 的显示驱动不提供 Desktop Duplication，`dxcam.create()` 会失败或 `grab()` 持续返回 `None`，现在只会抛"DXcam 没有返回画面帧"。**根本到不了分辨率校验那一行。**
2. **显示模式**。无显示器的 VM 默认 1024×768。没有可用的虚拟显示输出时，1440p 不是"要不要适配"，是设不上去。
3. **会话存活**。RDP 断开后会话可能进入非交互状态，采集停止、`SendInput` 落空。这是长跑无人值守的隐形杀手，比分辨率严重得多。
4. **分辨率与布局**（最后才轮到）。

结论：**先解采集和会话，再谈通用性。** 如果帧都拿不到，后面所有方案的收益都是零。

关于虚拟显示器驱动（IDD）：这是解决第 2 项的标准手段，但 [可行性文档 §2](apex-ui-drop-screenshot-feasibility.md) 已明确把"未经云服务商允许的驱动或虚拟硬件修改"排除在范围外，§10 也把"允许安装所需输入驱动"列为上线前置。**因此它必须作为需服务商许可的前置条件对待，不能当成免费动作。** 若不获许可，则只能接受服务商给定的分辨率，通用性改造从"可选"变成"必需"。

采集侧的备选是 Windows.Graphics.Capture（WGC）——它在更多会话形态下可用，且原生支持按窗口捕获。可行性文档 §13 风险表里已经写了"提前验证 Windows.Graphics.Capture"，方向一致。**但目前项目里没有 WGC 实现，Python 绑定的可用性也未调研。**

## 4. 四种范式的可行性对比

| 方案 | 通用性 | 需重新标定 | 主要风险 | 评价 |
|---|---|---|---|---|
| A 钉死环境（虚拟显示器 + 固定 videoconfig） | 无 | 否 | 依赖服务商许可；驱动更新即全线故障 | 短期正解，但不是答案 |
| B 纯比例归一化（坐标存 0..1） | 仅同宽高比 | 否 | **静默算错**：21:9 下算出"看着合理但点空"的坐标 | 不推荐单用 |
| C 锚点布局（声明贴边 + 偏移） | 较好 | **是，每分辨率两套图** | 与"别反复要求录制"的约束直接冲突 | 不推荐 |
| D 画布归一化（接缝处可逆变换） | 16:9 家族 | 否 | 上采样后 OCR 与模板相关性下降 | **性价比最高的一步** |
| E 语义定位（locator → 元素 → 框中心） | 任意分辨率与宽高比 | 否 | 误识别导致点错；OCR 成本 | **唯一能扛宽高比的解** |

D 与 E 不是二选一：D 提供"先在哪儿搜"的加速与非文字元素的尺度归一，E 决定最终点哪里。C 之所以否掉，是因为它要求为每个新分辨率补两套标定图，而 D+E 一张都不用补——语义描述本来就不含像素。

### 4.1 关于 B 的静默失败

值得单独强调：比例换算在 21:9 下**不会报错**。Apex 的菜单在超宽比下不拉伸、HUD 贴边，布局法则变了，但比例公式照样能算出一个落在屏幕内的整数坐标。这类"算出一个合理但错误的值"比直接崩溃危险得多，与 [§9.4 的安全主线](resilient-task-runner-design.md)（不确定就暂停、不猜）相抵触。

## 5. 与既有决定的关系

这是本文最需要说清楚的一节。

[可恢复任务运行器设计 §9.4](resilient-task-runner-design.md) 已经定过：

> 执行原语上也要区分「识别」与「消除」：识别用 OCR / 模板，**消除过场页优先用键盘**（Esc/Enter/Space），而不是「OCR 定位到按钮再点坐标」——键盘推进对布局变化健壮得多。

本文提出的方案 E 表面上正是那条决定否掉的东西。必须正面回应：

1. **那条决定是对的，而且应该扩大适用。** 键盘推进不依赖分辨率、不依赖宽高比、不依赖 OCR 出框，是通用性最高的原语。当前 12 条点击里，有多少能改成键盘导航（方向键 + Enter）而不是点坐标，应当先逐条评估——**这比引入任何新机制都便宜**。
2. **语义定位只适用于键盘到不了的地方。** 例如模式面板的卡片选择、"补满"复选框这类没有明确键盘焦点路径的控件。这些当前只能点固定坐标，等于没有退路。
3. **"识别与执行分离"在方案 E 下依然成立。** 分离的实质是"不要让识别的置信度直接变成执行的授权"。语义定位把"解析出目标框"做成一个独立的、可验证的、找不到就不执行的步骤，分离没有被破坏——反而比现在更强：**硬编码坐标永远能点到"某个东西"，UI 挪了照点不误；语义定位找不到就停，是 fail closed。**

第 3 点对一个长期无人值守的系统，价值可能高于通用性本身。

## 6. 建议的目标架构

核心思路：给每个坐标系起名字，坐标系之间的变换做成显式对象，坐标不脱离坐标系单独存在。

| 层 | 职责 | 坐标系 |
|---|---|---|
| 0 采集 | `FrameSource` 产出 `(frame, geometry)`，多后端，优先按窗口抓 | 屏幕空间 |
| 1 几何 | `ViewTransform`：屏幕 ↔ 规范空间的**可逆**变换 | 两者之间 |
| 2 感知 | 帧 → `UiElement{role, text, box, confidence}` 列表 | 规范空间，**从当前帧推导** |
| 3 状态 | 对**元素集合**求谓词 | 无坐标 |
| 4 定位 | locator → 元素 → 框中心 | 规范空间 |
| 5 执行 | 规范点 → 逆变换 → 屏幕点 → `SendInput` | 屏幕空间 |
| 6 校验 | 动作断言后置状态 | 无坐标 |

**全流水线只有第 1 层知道分辨率。**

第 3 层是重心：region 从"真理"降级为"提示"。现在 `bottomRight: [1360, 760, 2560, 1440]` 是判定前提，错了就判错；改造后它只是"优先在这块搜以省 OCR 时间"，搜不到可扩大范围，正确性不再依赖它。

配置形态的变化：

```json
// 现在
"guideAccountContinue": [610, 150]

// 目标
{
  "id": "guideAccountContinue",
  "prefer": { "key": "ENTER" },
  "match":  { "text": "继续", "role": "button" },
  "hint":   { "anchor": "topRight", "within": [0.7, 0.0, 1.0, 0.25] },
  "expect": { "minConfidence": 0.8, "boxArea": [0.002, 0.05] }
}
```

`prefer` 体现键盘优先，`match` 是分辨率无关的真理，`hint` 是允许出错的加速器，`expect` 是防误点的闸门。这份描述在任何分辨率和宽高比下都不需要重录。

### 6.1 非文字元素

OCR 覆盖不到 HUD、图标、小地图。按代价排序：规范空间内的多尺度模板匹配（第 1 层已归一尺度，金字塔范围可以很窄）→ 特征匹配（ORB/AKAZE + 单应性，尺度旋转不变）→ 训练小检测器。前两者预计够用。

### 6.2 性能

全帧 OCR 已实测 425.4 ms（[OCR 标定文档](ocr-first-calibration.md)），不可能每帧解析。两级方案：高频跑 `vision.py:56` 已有的 `frame_delta`，画面稳定则复用上次元素列表，仅在变化或动作前重新解析。等于给感知层加缓存，失效条件是运动量。

## 7. 分阶段实施与验收

沿用既有的"任一项失败即停"约定。

| 阶段 | 内容 | 验收 |
|---|---|---|
| 0 | 云环境采集与会话闸门：确认 dxcam/DXGI 是否可用；不可用则实现 WGC 或 GDI 兜底；确认会话断开后采集与输入是否存活 | 目标云上连续 30 分钟拿到非黑屏帧且输入生效 |
| 1 | `ViewTransform` + 画布归一化，接入 `capture.py` 与 `input_win32.py`；`progression.py` 的 ROI 提到配置 | 现有全部离线用例在 1080p 与 4K 输入下通过 |
| 2 | 逐条评估 12 个点击能力能否改键盘导航 | 每转换一条，在目标机器实测后置状态确认 |
| 3 | 剩余点击迁移到语义定位；region 降级为 hint | 找不到目标时不执行且记录未知帧 |
| 4 | 配置卫生：四份无分辨率标识的文件补 `referenceResolution` | 装载时校验声明与实际一致 |

阶段 0 的优先级不可调整——它是其余阶段的前置。阶段 2 应排在阶段 3 之前，因为它更便宜且不引入新机制。

## 8. 明确不做

- 不绕过反作弊，不做检测规避；
- 不为通用性牺牲"不确定就暂停"的安全主线；
- 不引入需要为每个新分辨率补充标定图的方案（方案 C）；
- 不在未获服务商许可的前提下安装虚拟显示或输入驱动；
- 不追求语言、键位、赛季 UI 版本的同时无关性——本文只覆盖几何维度。

## 9. 待验证的未知数

以下均**未经实测**，实施前需逐项确认，不应按推测排期：

| 未知数 | 影响 | 如何验证 |
|---|---|---|
| dxcam 在目标云环境是否可用 | 决定阶段 0 工作量 | 云上跑一次现有 `observe` |
| WGC 是否有可用的 Python 绑定 | 决定兜底方案成本 | 调研；无绑定则需 C 扩展或换语言边界 |
| 1080p 上采样到 1440p 后 OCR 置信度 | 决定方案 D 是否够用 | 用既有帧降采样再升采样，跑现有 OCR 用例对比 |
| 模板匹配在重采样帧上的相关性下降幅度 | 决定阈值是否要放宽 | 同上 |
| Apex 在 21:9 下的实际布局 | 决定方案 E 的紧迫性 | **当前无任何样本** |
| 12 条点击里有多少能改键盘导航 | 决定阶段 3 的规模 | 目标机器上逐条试 |

最后一项建议最先做：它可能大幅缩小后续所有工作的范围，而且只需要在已有环境上操作，不需要新环境、不需要新代码、不需要补标定图。
