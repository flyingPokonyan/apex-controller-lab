# 升级速度与停滞：8 月 3 日两段跑的复盘

> 数据全部来自 ApexForge 服务端（`apex_runs` / `apex_level_snapshots` / `apex_run_events`），
> 不是回忆，也不需要目标机器上的截图。两段跑分别是 `20260803-083835-cd21eb63`（run 3）
> 和 `20260803-134939-aedf242a`（run 4）。

## 一句话

**每分钟约 220 点经验是这个模式挂机的真实速率，40-60 分钟一级没算错；
真正丢掉的时间不在对局里——run 3 有 75 分钟停在一张没人认识的画面上。**

## 两段跑的骨架

| | run 3 | run 4 |
|---|---|---|
| 本地时间 | 08:38:35 → 13:35:25 | 13:49:39 → 15:03:55 |
| 墙上时间 | 4 小时 57 分 | 1 小时 14 分 |
| 等级 | 9 → 14（最后一次读数 14 级 6820） | 14 → 15（最后一次 15 级 10100） |
| 结束方式 | **没有结束**：`state=RUNNING`，没有 `RUN_FINISHED` | 同上 |
| 最后的错误 | `UNKNOWN_SCREEN` | `UNKNOWN_SCREEN` |

两段都不是「断线」——心跳一直在报，`foreground: true`，帧数一直在涨。断的是**进展**。

## 一、停了 75 分钟，而不是断了

run 3 的最后一段事件流：

```
04:07:12  post-match-return-lobby 确认 → LOBBY_READY_TARGET
04:07:13  点「准备」→ LOBBY_QUEUEING（确认）
04:08:57  跳伞机 → 04:09:07 进对局
04:18:45  死亡 → 观战 → 04:19:59 结算
04:20:23  回到大厅 LOBBY_READY_TARGET（后置确认拿到）
04:20:32  未知画面，存证 screenshots/399-unknown.png
04:30:41  未知画面，存证 screenshots/400-unknown.png
04:30:41 → 05:35:25   只有心跳。actionsSent 卡在 2403 一次没动，
                      observedState 一直是 null，帧数从 30k 涨到 35k
```

**75 分钟，一次输入都没发，一次状态都没变。**run 4 死在同一个地方：结算后
`returnLobbySequence` 发了两次，06:58:05 起画面变成未知，5 分半后上报整个停止。

按 220 点/分钟折算，run 3 这一段丢掉的是**约 16000 点经验，一级半**。

两件事同时成立才会这样：

- **没有规则认识那张画面**，所以调度器永远拿不到可以动手的状态；
- **没有任何东西在意「多久没动了」**。环检测管的是「动作在原地打转」，
  一次都没动手反而不算环。

那张画面是什么，本地已经有证据（`399/400-unknown.png`、run 4 的
`095/096-unknown.png`），在目标机器的 `windows\runs\<run>\screenshots\` 里。
在拿到它之前，先按「不认识也得有出路」处理。

### 改法：看门狗 + 认字点按钮

新增 `STALLED_UNKNOWN`。它不是任何字典里的页面，而是运行器对自己的判断：
**快速识别和覆盖层 OCR 连续两分钟都认不出这一帧**。要求两个识别层同时哑掉，
所以「大厅认得出、只是覆盖层 OCR 挂了」这种情况不会被当成停滞——那是运行器
在刻意不动手，不是没人认识这张画面。

按下「准备」之后的那段黑屏单独算：排队、选传奇、读条本来就没有名字，
8 月 3 日实测 72、104、116 秒，两分钟没有余量，而在这段时间里乱按 ESC
可能把队列取消掉。所以它的宽限是七分钟（`queueGraceMs`）。实际见到的两次停滞
都发生在回到大厅之后，走的是两分钟那条。

挂在它上面的 `stall-recover` 不是盲点：它全屏 OCR，找页面**自己写着的**按钮字
（继续、重试、确定、接受、返回大厅、好的、关闭、返回），**点在读到那几个字的位置上**。
词按优先级排序，断线弹窗上同时有「重试」和「返回」时点重试。两种情况下它不点：
OCR 一个词都没读到，或者引擎降级成逐区域读、没有返回文字坐标——那时退回按 `ESC`，
因为「知道屏幕上有个继续」不等于「知道该点哪」。

节奏是有限的：一轮 20 秒最多试三次，隔三分钟再来一轮，两轮之间那张画面又变回
普通未知画面，谁都不许碰。半小时仍未恢复就结束会话（`STALL_UNRECOVERED`），
租约按 `RELEASED` 关掉、原因写明，而不是继续报一整夜的 `RUNNING`。

`STALL_DETECTED` / `STALL_RECOVERED` / `STALL_UNRECOVERED` 都会上报，
所以下次这种事在控制台上是看得见的。

## 二、升级速度：慢是真的，但慢在哪里可以量

服务端的等级快照给出了确定的速率：

| | 区间 | 经验 | 用时 | 速率 |
|---|---|---|---|---|
| run 3 | 9 级 7210 → 14 级 6820 | 44860 | 3 小时 27 分 | **216 点/分钟** |
| run 4 | 14 级 9580 → 15 级 10100 | 10920 | 49 分 40 秒 | **220 点/分钟** |

每级所需经验随等级上涨（9→10 是 8150，14→15 是 10400，往后每级约 +450），
所以同样的速率下：

| 升级 | 所需经验 | 按 220 点/分钟 |
|---|---|---|
| 14 → 15 | 10400 | 47 分钟 |
| 15 → 16 | 10900 | 50 分钟 |
| 19 → 20 | 12700 | 58 分钟 |
| **15 → 20 合计** | **59000** | **约 4.5 小时** |

「40-60 分钟一级」是对的，而且它会随等级变慢。

### 一局是怎么花掉的（run 4 实测四局）

| 局 | 时长 | 经验 | 说明 |
|---|---|---|---|
| 1 | 14 分 49 秒 | +3560 | 完整一局 |
| 2 | 15 分 31 秒 | +3370 | 中途死一次，队友把局撑到 06:20 |
| 3 | **4 分 40 秒** | **+420** | 落地 15 秒就死，队伍很快团灭 |
| 4 | 14 分 17 秒 | +3570 | 完整一局 |

一局的时间构成（同一次跑的相位事件）：

```
排队      72 - 117 秒
跳伞+自由落体   35 -  45 秒
存活      5 - 12 分钟      ← 经验主要来自这里
观战      50 - 285 秒      ← 死了但队友还活着，只能等
结算+大厅  15 -  35 秒
```

### 观战不是白等：经验按**小队**幸存时间给

把两段跑的 22 局按「存活秒数」「观战秒数」「这一局涨了多少经验」拆开，做最小二乘：

| 模型 | R² | 系数 |
|---|---|---|
| 经验 ~ 存活 | 0.624 | 4.33 点/秒 |
| **经验 ~ 整局时长（存活+观战）** | **0.929** | **4.27 点/秒，截距 ≈ 22** |
| 经验 ~ 存活、观战分开 | 0.936 | 存活 **4.55**、观战 **3.83** 点/秒 |

**观战每秒 3.83 点，是存活的 84%。**几乎所有经验都只和「这一局打了多久」有关，
和「我活着没有」关系不大——因为 Apex 给的是小队幸存时间。截距接近 0 也说明
这个模式没有多大一笔结算固定奖励，经验基本是纯时间。

所以「死了立刻退出重排」不划算：

```
现在这样（死了等队友）  223 点/分钟
死了立刻退出重排        221 点/分钟   (-0.8%)
```

省下的观战时间要拿去重新排队和跳伞（每局固定开销约 145 秒），而观战本来就在
按 84% 的速率发钱。退出更划算的条件是**平均存活超过 12.9 分钟**，实际是 10.3 分钟。
真要做这件事还得先回答一个没人验过的问题：中途退出会不会把这一局已经攒的经验
一起丢掉。收益 -0.8%，不值得冒这个险。

顺带得到一个上限：整局时长每秒 4.27 点，也就是**理论上限 256 点/分钟**；
实际 223，差的 13% 全是每局那 145 秒排队加跳伞。这个模式挂机就是这个速度，
再快只能换模式——而换哪个模式更快，现在手上一局数据都没有，得先跑一局量。

### 所以能做什么

| 做什么 | 能拿回多少 | 状态 |
|---|---|---|
| 不再停在未知画面上 | run 3 的 25% 墙上时间 | 本次已改 |
| 停不下来时把会话结束掉，而不是假装在跑 | 让无人值守的夜里不再白跑 | 本次已改 |
| 死后不等队友，直接退出去重排 | **-0.8%** | 量过了，**不做** |
| 压缩每局 145 秒开销 | 最多 13% | 排队时间不由我们决定，能压的只有结算那 20 秒 |
| 活得更久（整局打得更久） | 每多一分钟 +256 点 | 要读地图往圈里走，是另一个工程 |

## 三、放战术技能，和「默认选某个英雄」

**Q 已经加了**：`in-match-tactical`，闸门和近战一样是 `IN_MATCH_ALIVE`，
每 9 到 12 秒一次，`idempotent`——冷却好了就生效、没好就什么都不发生。
扫描码 16（Q），已写进 `_keyBindings`。顺手修了调度器一个会挡路的地方：
同一张画面上有两条周期能力时，原来只有优先级最高的那条能触发，
排在后面的永远轮不到；现在每条各按各的间隔。

**选英雄还差一张图，但不用专门去录。**传奇选择页落在「按下准备」到「跳伞机」
之间那段没有任何规则认识的画面里，通用取证是 20 秒采一次、并且会跳过和上一张
几乎一样的帧——而这一页除了倒计时基本是静止的，正好被跳过：8 月 3 日两段跑
一共只留下三帧。

所以加了 `legendSelect`，做两件都不发输入的事：

- **留帧**：排队之后这段空白里每 5 秒留一帧，只留前两局，文件名就叫
  `NNN-legend-select.png`；
- **探针**：同一段里全屏 OCR 最多五次，把整页读到的文字连坐标写进
  `LEGEND_SCREEN_TEXT`，并单独记一条 `LEGEND_NAME_FOUND`——目标是
  `preferredLegend`，现在配的是**命脉**。

探针是为了回答两个决定做法的问题，而这两个问题看一眼日志就有答案：

| 问题 | 日志里怎么看 | 答案决定了什么 |
|---|---|---|
| 名字画在卡片上吗 | 有没有 `LEGEND_NAME_FOUND` | 有 → 直接用 `clickText`「点写着命脉的地方」，一个坐标都不用量 |
| 选完要不要再确认一下 | `LEGEND_SCREEN_TEXT` 里有没有「锁定」「选择」这类词 | 决定是一步还是两步 |

没找到也是答案：那就说明卡片上只有头像，改成量一次网格坐标——切号跑的都是新号，
英雄解锁一致，量一次能一直用。

**探针一次都不点。**在传奇选择页上乱点是会选错英雄的，而这份日志跑一局就有，
不值得抢这一局。在它出结果之前，进对局的英雄仍由游戏自动分配，
`in-match-tactical` 放的就是它的 Q。

## 复现这些数字

服务端在 `ssh igw` 的 `~/apex-forge/backend/data/apexforge.db`：

```sql
-- 每次跑的骨架
SELECT client_run_id, state, result, last_error_code, started_at, last_heartbeat_at FROM apex_runs;

-- 等级/经验时间线（这份文档里的速率就是从它算的）
SELECT run_id, observed_at, level, xp_current_approx, xp_required_approx
FROM apex_level_snapshots ORDER BY run_id, event_sequence;

-- 一局的相位构成（存活/观战/排队各多少秒，上面那个回归就是从它和等级快照拼出来的）
SELECT sequence, occurred_at, json_extract(payload_json,'$.phase')
FROM apex_run_events WHERE run_id=4 AND type='MATCH_PHASE_CHANGED' ORDER BY sequence;
```

下一次跑完，这两条看传奇选择的结果（在 Runner 本地 `events.jsonl` 里，不上报）：

```powershell
Select-String -Path .\windows\runs\<run>\events.jsonl -Pattern 'LEGEND_NAME_FOUND'
Select-String -Path .\windows\runs\<run>\events.jsonl -Pattern 'LEGEND_SCREEN_TEXT'
```
