# 菜单改用文字证据：离线测量与待实测项

> 日期：2026-07-29
> 状态：在 macOS 上用本地留存的原始标定帧测得；**这些是录像帧不是实时 DXGI 帧**，
> 所有结论都要用 `observe` 的实测数据复核。

## 1. 为什么要改

模板得分在离线验证里全是 `1.000`，因为模板就是从同一张原图按同一坐标裁下来的
（逐字节相同）。这个数字不含信息量。把模板互相打分才看得到真实余量：

| 比较 | edge-F1 | 该状态阈值 | 余量 |
|---|---|---|---|
| `lobby-training-ready`（准备）vs `lobby-mode-select`（选择） | 0.712 | 0.84 | 0.128 |
| `lobby-training-card`（训练）vs `lobby-match-card`（匹配） | 0.546 | 0.62 | **0.074** |

余量最小的那个恰好是判断"大厅当前是不是目标模式"的依据，而 `lobby-match-card.png`
里烤进了**实时倒计时**（"12分钟58秒"）和**会轮换的地图名**（"风暴点"）。
`lobby-training-ready.png` 里还烤进了**鼠标光标**，但运行时点击后光标会被移到屏幕中心。

## 3. 建议的 OCR 区域

替代现在 `tutorial-states.zh-CN.json` 里所有规则共用的 `fullFrame`
（2560×1440）。合计约占全屏 19%，且每次只需要跑候选规则涉及的区域。

```json
{
  "lobbyModeName":      [60, 1060, 420, 1140],
  "lobbyPrimaryButton": [1200, 1240, 1360, 1340],
  "guideBanner":        [400, 80, 1870, 320],
  "modePanelHeader":    [1000, 10, 1600, 100],
  "modePanelCore":      [380, 640, 660, 1180],
  "exitMenu":           [1180, 700, 1400, 870],
  "exitConfirm":        [1100, 530, 1420, 700]
}
```

## 3.1 区域必须是"紧致单行"，否则省不下时间

在 macOS/arm64 上用同一张大厅帧实测（PP-OCRv6 small，onnxruntime CPU）：

| 输入 | 方式 | 耗时 | 读出 |
|---|---|---|---|
| fullFrame 2560×1440 | det+cls+rec | 425.4 ms | 23 个文本块 |
| lobbyModeName 360×80 | det+cls+rec | 233.7 ms | `未上榜` |
| lobbyModeName 360×80 | **rec only** | **4.7 ms** | `未上榜` |
| lobbyPrimaryButton 160×100 | det+cls+rec | 86.5 ms | `准备` |
| lobbyPrimaryButton 160×100 | **rec only** | **5.0 ms** | `准备` |
| modePanelCore 280×540 | det+cls+rec | 173.4 ms | 7 个文本块 |
| modePanelCore 280×540 | rec only | 4.4 ms | `新`（错） |

**只裁小区域几乎不省时间**：检测模型会把输入缩放到自己的固定工作分辨率，
所以检测开销和原始尺寸基本无关。真正的差别在于**能不能跳过检测**。

- ROI 紧到只含一行字 → `use_det=False, use_cls=False` → 约 5ms
- ROI 含多行 → 必须走检测 → 约 175ms（rec only 会读出垃圾）

一轮大厅判断（模式名 + 主按钮两个单行 ROI，rec only）合计 **9.2ms**，
相比现在 `fullFrame` 的 425ms 快约 46 倍。1s 扫描间隔绰绰有余，
300ms 也没问题。

这要求 `RapidOcrProvider` 支持按区域声明单行模式；区域字典需要加
`"singleLine": true`。绝对数字取决于 CPU，但比例同源同代码路径，实测复核。

## 4. 离线测出来的三个问题

### 4.1 `unrankedMatchClick` 点在了已锁定的排位赛卡片上

`first-tutorial-2560x1440.zh-CN.json` 配置 `unrankedMatchClick: [540, 835]`。
在 `MODE_PANEL_MATCH` 模板所裁自的那张帧上：

- `已锁定`（排位赛卡片）位于 [420,784 508,821]
- `未上榜` 位于 [414,1001 574,1068]，`三人赛` 位于 [419,1054 530,1099]

y=835 落在排位赛卡片下沿，距离真正的未上榜卡片约 200px。这是一个 commit 级动作
（会切换游戏模式）点在了一个盲坐标上，而离线验证永远发现不了——它只验证识别，
不验证坐标。正确坐标需要在实测帧上重新标定，约在 [494, 1035] 附近。

### 4.2 退出菜单和退出确认都含有"返回大厅"

两屏都能读到 `返回大厅`。区分只能靠退出确认独有的 `是否离开？`。
任何只匹配"返回大厅"的规则会同时命中两屏。

### 4.3 导览页底下的大厅读数是"训练 + 选择"

四张导览页在覆盖层下方都能读到 `训练`（模式名）和 `选择`（主按钮）。
所以"看到训练就去开模式面板"的规则会在导览覆盖层还在时触发并点空。
**清除导览的优先级必须高于选择模式**——这不是猜测，是测出来的。

## 5. 建议：用 OCR 做静态坐标的前置校验

设计文档 §9.4 禁止"OCR 定位按钮再点"，理由是定位错了会点到任意位置。这个判断保留。

但可以在不放开点击范围的前提下加一道守卫：**点击坐标仍然写死在配置里，
执行前要求目标文字出现在该坐标附近的容差框内，否则不点、暂停留证。**
它不扩大任何可点范围，只会拒绝已经错掉的坐标——4.1 那种问题会在第一次就被挡下。

## 6. 必须由实测复核的项

- 全部置信度和 ROI 是否在实时 DXGI 帧上成立（录像帧偏干净）
- 区域 OCR 单次耗时，决定扫描间隔能不能做到 1s
- `未上榜` 卡片的实测坐标
- post-match 全流程（淘汰、结算、回大厅）——目前零素材
- 登录过场视频的 `motion` 实测值，用来定 `HIGH_MOTION` 阈值（当前占位 0.02）
