# 能力证据矩阵与当前进度

> 更新：2026-07-30。所有 ROI、置信度、阈值余量均取自目标机器
> （`2560×1440`、中文、全屏）的实时 DXGI 帧，不是录像帧。
> 能力集从这一版起真的会执行——见[闭环怎么跑起来的](#闭环怎么跑起来的)。
>
> 全局进度、采集数据台账、闭环三段各自的证据强度在[现状汇总](current-status.md)，
> 本文只管每条能力靠什么帧成立。

## 为什么需要这张表

加一条能力需要**两张**帧，不是一张：

1. **触发帧** —— 用来写识别规则；
2. **动作后应看到的帧** —— 用来写后置确认，`toggle` 和 `commit` 必须有。

第一轮采集只按"有哪些画面"列清单，漏了第二类，结果是做到某条能力才发现少东西。
以后每加一条能力，先在这张表里补一行，再决定要不要采集。

## 排队中（大厅按下「准备」之后）

最后一块挡住闭环的证据。这条规则先按录屏写错过一次，再按 `20260729-235005`
实时场次的 144 张全屏帧改对，过程本身值得记下来。

**最终判据只有一条：`lobbyPrimaryButton` 读到「取消」。**

这是全文件唯一一条单区域规则，其他大厅态都要两处证据。原因是第二处证据试过、
不成立：模式卡片下方那几行会随模式和子状态**变行数**。

| 画面 | 卡片下方实际有几行 | 各行内容（实测 y 区间） |
|---|---|---|
| 未上榜 空闲 | 2 | 三人赛 `1299–1321` / 诸王峡谷｜59分钟59秒 `1329–1348` |
| 未上榜 排队中 | 3 | 三人赛 `1258–1281` / 正在匹配…… `1293–1311` / 18名玩家正在排队 `1318–1340` |
| 未上榜 正在连接比赛 | 2 | 三人赛 `1299–1321` / 正在连接比赛 `1328–1347` |
| 训练 排队中（录屏） | 1 | 正在匹配…… `≈1330–1352` |

没有任何固定的单行框能同时框住这四种排布——按录屏量的 `[70,1312,350,1366]`
在实时大厅里正好横跨两行，`singleLine` 的前提当场破掉。

主按钮反而是全场最稳的读数：

| 证据 | 排队时读到 | 来源 |
|---|---|---|
| 训练模式排队 | 取消 | 2026-07-28 录屏 |
| 控制模式排队 | 取消 | `20260728-234103` 全屏 OCR 日志 |
| 未上榜排队 ×2 段 | 取消 | `20260729-235005` 实时 DXGI 帧 |
| 正在连接比赛 | 取消 | 同上 |

反向也查过：把这个 ROI 从那 144 张实时帧上全部裁出来逐张看，「取消」**只**出现在
两段排队里，其余帧读到的是「准备」「进行中的…」「与基地相连的…」「LCTRL 单独发射」
「重生在…」——都不含「取消」。

单区域在这里可以接受，还因为**认错的代价最小**：`LOBBY_QUEUEING` 没有任何能力，
误判最多让运行器多等一帧，不会多发一次输入。

时间余量：

| 事情 | 实测 | 来源 |
|---|---|---|
| 按下到按钮变字 | ≤ 100 ms | 录屏 10fps 采样 |
| 未上榜排队持续 | **38 s**（605→643 s） | `20260729-235005` |
| 控制模式排队持续 | ≥ 43 s | `20260728-234103` |
| 训练模式排队持续 | 约 8 s / 另一次上限 6.8 s | 录屏、日志 |

`confirmMs` 取 3000，稳稳落在真人匹配队列里。训练模式那两次快得多（打机器人几乎
秒开），但训练大厅归 `lobby-open-mode-panel`，这条能力遇不到。

万一还是错过了——窗口到期时已经在读条——后置确认拿不到 `LOBBY_QUEUEING`，但那时
当前画面已经不是大厅，重试会被下面这条规则丢弃，不会误点：

> 确认窗口过期后，调度器原来会**不管当前画面是什么**都重试一次。按下「准备」到
> 跳伞机之间隔着传奇选择和读条——实测将近一分钟没有任何规则认识的画面——那次迟到的
> 重试会把大厅按钮的坐标点在对局里（鼠标左键＝开枪）。现在只有当前画面仍属于该能力
> 时才算重试，否则丢弃。

## 大厅主按钮：一个坐标，三个按钮

`[1280, 1295]` 那一格上写的字会变，写什么就干什么：

| 按钮读到 | 点下去发生什么 |
|---|---|
| 选择 | 打开模式面板 |
| **准备** | **排进当前卡片上那个模式** |
| 取消 | 退出队列 |

第一次真跑 `play` 就栽在这里：`lobby-open-mode-panel` 同时挂着
`LOBBY_SELECT_REQUIRED` 和 `LOBBY_READY_TRAINING`，两个状态点同一个坐标。前者
按钮写「选择」，开面板；后者写「准备」，**直接进训练场**。这条能力的注释里原本就
写着「训练模式按准备会进训练场」，然后干的正是这件事。

2026-07-28 的日志逐字记着这个后果：

```
66271ms  ACTION_SENT modeSelectClick x=1280 y=1295   （训练大厅）
79807ms  STATE_UNKNOWN                                （读条）
93777ms  TUTORIAL_MOVEMENT                            （已经在训练场里）
```

现在拆成两条：写「选择」时才点主按钮，其余一律点左下角模式卡片
（`[308, 1215]`，卡片实测占 `x 62-555`、`y 1065-1365`）。有测试盯着这条不变式：
**任何点主按钮的能力，只能绑在规则本身钉死了按钮字样的状态上，且「准备」只有
`LOBBY_READY_UNRANKED` 能点**——因为只有它同时钉死了模式名。

顺带补上一个会让闭环原地卡死的洞。原来只有模式名读到「训练」或「未上榜」时大厅才
被认识；2026-07-29 那帧读到的是「控制」+「准备」，**整个大厅识别为 None**，一局
打完回来运行器就在那儿站着不动了。新增的 `LOBBY_READY_OTHER` 只看按钮读到「准备」，
靠**排在其他大厅规则之后**来表达「非训练也非未上榜」——先匹配先赢是这套规则里唯一
能表达「非」的手段，所以它必须永远是最后一条，这一点也有测试盯着。它同样只会去点
模式卡片换模式，绝不碰主按钮。

## 键位是假定，不是事实

2026-07-30 第一次真跑，近战发了 9 次，游戏里一下都没挥。查了半天怀疑到反作弊
拦截合成输入头上，结果是：**目标账号把近战绑在 N 上，配置里写的是 V。**

这件事值得单独记一段，因为**错的扫描码和送不到的输入，在画面上完全一样**：动作发出去了，
截图上什么都没变。任何靠看截图的诊断都区分不了这两者，所以有了
`windows/probe-input.cmd`——它发六个明显可见的动作（前进、横移、近战、蹲下、
转视角、开枪），由人来回答哪几个真的发生了。那一次的答案是「都有」，一句话就把
「输入进不去」这个假设排除干净了。

`enter-game.zh-CN.json` 里现在有一段 `_keyBindings` 写明每个扫描码假定的是哪个键，
并且有测试盯着：**任何按键能力用到的扫描码，都必须在那段说明里出现过。**

## Apex 里有一批提示是长按，不是点按

同一次会话里 `LCTRL` 的 80ms 点按在跳伞机上没生效，而同一枚扫描码在训练场里能正常
蹲下——键送到了，是那个提示不吃这么短的一下。操作者确认「单独发射」要长按。

这不是孤例，是这个游戏的一类交互。已知的至少两处：

| 提示 | 实际要求 | 现状 |
|---|---|---|
| 跳伞机「LCTRL 单独发射」 | 长按 | `dropship-detach` 设了 `holdMs: 800`，**未实测** |
| 结算页 TAB 之后弹出的页 | **长按 SPACE 才真的返回大厅** | **还没有能力，也没有证据帧** |

所以按键能力有了自己的 `holdMs`：默认的 `keyTapMs` 是给菜单点按用的，长按提示必须
逐条声明。

第二行是当前 `post-match-return-lobby` 的缺口：它只发 TAB，而 TAB 之后还有一页要
长按 SPACE。四份采集里都没有这一页——`长按` 在数据里只出现在跳伞 HUD 的
「长按5表情菜单」「长按…进入自由视角」。

为了不再靠人去复现，`CapabilityPilot` 现在会**给自己不认识的画面留证**：状态连续
8 秒是 `None` 就存一帧，每段只存一次（读条也会被拍到，这就是宽限给到 8 秒的原因）。
下次跑到结算页，那一页会自己出现在 `screenshots/` 里。

## 闭环怎么跑起来的

能力集原先只有 `observe` 会加载，而 `observe` 按设计不发输入；`start` 走的是老的
有序 supervisor，它根本不认识 `enter-game.zh-CN.json`。也就是说在 2026-07-30
之前，**没有任何路径会真的执行这些能力**。

现在有了：`windows/play.cmd` → `run.ps1 play` → `CapabilityPilot`。

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| `game-states.zh-CN.json` | 这帧是什么画面 | 该不该动手 |
| `enter-game.zh-CN.json` | 每个画面能做什么、做完该看到什么 | 什么时候轮到它 |
| `CapabilityDispatcher` | 同一帧内仲裁、重试预算、后置确认、环检测 | 怎么把输入发出去 |
| `CapabilityPilot` | 前台校验、发输入、判定后置、记证据 | 画面顺序（没有顺序） |

`play` 用自己的画像 `play-2560x1440.zh-CN.json`，里面没有模板、没有离线用例、
没有 `task.actions` 那张有序动作表——能力集就是用来取代它们的，让它被继承回来
只会出现两套互相不知道对方存在的动作表。

三条硬性安全性质，都有测试兜着：

- 认不出画面就不发任何输入（`decide(None)` → `NO_STATE`）；
- 每次发送前**紧挨着**再查一次前台，切走就 `release_all` 并作废待确认动作；
- 无论怎么结束（到时、F8、Ctrl+C、异常），`finally` 都会把按键放开——绝不在对局里
  留一个按住的键。

`toggle` 的安全性也是端到端验过的：跳伞机画面停着不动时，`LCTRL` 只会按一次，
之后走 `ATTEMPTS_EXHAUSTED` 暂停，而不是按第二下把自己送回小队。

## 有意不做能力的画面

能自动过去的画面就让它自动过。能力越少，越不容易在计划外的画面上出错。

| 画面 | 为什么不做 |
|---|---|
| 排队中 | 那上面只有「取消」，任何输入都只会退出刚加入的队列 |
| 英雄选择 | 超时自动选，不需要输入 |
| 娱乐模式开局选武器 | 实测超时会自动分配一套，照样进对局 |
| 控制模式选出生点 | 同上，预计也会超时自动分配（待确认） |
| 观战 / 死亡回放 | 此时任何输入都无意义；近战闸门刻意不覆盖它 |
| 登录过场视频 | 约 60 秒后自行结束，主动长按空格探测不划算 |
| 断连回到继续页 | 继续页已有能力，断连恢复是它的副产品 |

## 控制模式全程不被识别

`20260729-235005` 里第一局打的是控制模式，八分钟、747 帧中 621 帧
（83%）是 `NO_STATE`，`in-match-melee` 一次都没触发。原因很干净：

同一个 `squadCountAlive` 区域、同一个位置、同样是单行——

| 模式 | 读到 |
|---|---|
| 大逃杀 | `17 剩余小队数量` |
| 控制 | `剩余时间： 25:58` |

`in-match-alive` 只认「剩余小队数量」，控制模式永远不出现这几个字。

**没有顺手改成「两者取其一」，是因为闸门的语义是「还活着」，不是「对局进行中」。**
把那 83 张控制模式的帧全裁出来看过：`剩余时间` 那条横幅几乎每帧都在，中间死亡、
重生都没让它消失。改成 `any` 会让近战在死亡和重生选点界面里照按不误，正好破坏
这个闸门唯一的作用。

要补的是**控制模式死亡/重生那一帧**：拿到它才能写出「活着才算」的判据。
在此之前控制模式就是全程空转——闭环照样闭得上（结算页正常出现、正常回大厅），
只是对局里不做事。

## 仍缺的证据

| 缺什么 | 挡住什么 |
|---|---|
| **结算页按 TAB 之后那一页** | `post-match-return-lobby` 只发了 TAB 就以为完事了；那一页要长按 SPACE。这是目前唯一挡住「一局接一局」的一环 |

| **登录后那串页面**（公告、纪念、欢迎、导览、奖励、升级） | 冷启动闭环。三次采集全是从大厅开始录的，这串页面一次都没进过样本 |
| 模式面板「自由式」栏的实时帧 | 选择娱乐模式 |
| 娱乐模式大厅的模式名 | `lobby-ready-entertainment` |
| 娱乐模式结算页 | 娱乐模式的 post-match（可能与匹配不同） |

第二行是目前唯一影响「能不能全自动」的一条：`play` 从大厅起跑没问题，但从桌面
双击 Apex 起跑会停在登录后的公告页上等人。要补它，得在**游戏启动那一刻**就开着
`observe`，而不是进了大厅再开。

无法主动制造、碰到再补：断连弹窗、匹配惩罚提示（必须归入人工暂停）。

## OCR 性能

| 方式 | 耗时 |
|---|---|
| 全屏 det+cls+rec | 2100–6800 ms |
| 单行紧致 ROI，跳过检测 | 4–16 ms |
| 一帧跑完全部区域 | 约 31 ms |

决定开销的是**文字检测**，且其成本与输入尺寸基本无关——只裁小区域省不下时间，
必须紧到只含一行字才能跳过检测。这是 `singleLine` 存在的原因。

## 采集数据位置

会话产出在 Windows 的 `windows/runs/<时间戳>/`，其中：

- `observations.jsonl` —— 逐帧得分、OCR 文本、决策；
- `observations-summary.json` —— 每状态得分分布与 `separation`；
- `screenshots/` —— 分类变化与去重后的定时截图。

原始全屏帧不进仓库；结论一律回填到本文与
[菜单改用文字证据](ocr-first-calibration.md)。
