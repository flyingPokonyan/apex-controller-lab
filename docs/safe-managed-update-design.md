# 托管 Runner 自动更新与故障恢复

## 需求和边界

`apex-controller-lab` 在 Windows 上领取账号、操作 EA/Apex，并向 ApexForge 上传运行状态、证据和等级。EA/Apex 更新及未覆盖页面仍需人工判断、修复代码。修复推送后，已接入启动器的机器应自行更新；正常机器等当前账号收口，故障机器不必先解决旧代码无法处理的问题。

首版使用原目录更新，跟踪 `origin/main` 的实际提交 SHA。保留现有 Forge 租约、上报协议和本机配置，不增加发布管理平台、签名包、多版本安装或自动回滚。安装失败可重试；业务代码错误不能靠更新器自动修好。

## 进程和更新流程

日常 `account-cycle.cmd` 启动独立的、仅依赖 Python 标准库的启动器。启动器运行托管 Python 子进程，每 60 秒检查远端提交，Git 操作禁止交互并有超时。拉取对象不会修改运行中的工作目录。

启动器自身文件随提交变化时，在旧 Worker 已退出、安装成功后也会自动重新加载；不会沿用已被修复的旧启动器直到下次人工重启。PowerShell 外层保留原运行/暂停意图。

1. 正常工作时只记录新提交。账号收口后、创建下一个领取请求之前，Runner 检查更新请求并退出。
2. 游玩主循环仍有响应时，未知画面和动作耗尽交给游戏状态机恢复或安全收口，更新器等待账号边界。EA 故障暂停可提前交给新版恢复；不能用阶段持续时间判断故障，文件校验和游戏更新也可能长时间正常进行。
3. 更新前请求旧进程协作退出。业务循环长时间没有响应时进行有限恢复；请求退出超过 90 秒且未持续进行清理才结束自己启动的进程树。仍有新鲜主循环心跳的关闭游戏、退出 EA、提交租约阶段最多给 10 分钟，确认进程退出后才写工作目录。
4. 在现有 `play.lock` 下执行 fast-forward 更新、按需安装依赖和导入检查。此锁也阻止手动游玩和更新并发。每次记录安装状态，安装中断后不能跳过未完成的依赖步骤直接玩。
5. 新版先走现有租约恢复/清理及报告补传，再允许新领取。更新可发生在旧租约尚未收口时，但不会删除 checkpoint/outbox、伪造完成、强制释放服务端租约。

更新不保证从原画面继续，可能需要重新关闭游戏、退出账号并开始下一轮。持有旧租约时，恢复必须先于普通 EA 领号前预检，避免同一个未知页面挡住恢复入口。未确认的领取请求继续沿用其幂等标识；Provider 的 `clientVersion` 不随 Git 提交改变。

## 故障、暂停和重试

- 主循环通过本机文件报告存活、当前阶段、确认停滞和成功账号数。续租线程活着不等于主循环有响应。
- 单次读取心跳文件失败沿用本次启动最后一次有效主循环心跳及其原时间戳；持续读不到且原心跳超过超时才恢复。每次新进程启动清空缓存，不能用上一进程的心跳确认新版。
- 主循环心跳是尽力写入的监控信息，短暂文件锁冲突不抛异常打断游戏；持续写入失败仍由启动器根据最后一次真实心跳超时处理。checkpoint 和报告 outbox 的持久化失败仍不能忽略。
- 恢复请求只打断游玩一次，后续关闭 Apex、退出 EA 和租约提交仍持续上报心跳；F8/人工停止仍可打断清理。收口阶段的 EA 错误保留原运行结果、等级证据和租约，不按登录失败重新提交失败结果。
- 网络和接口暂时不可用由现有重试流程处理；不能因此宣告任务完成。更新下载失败不打断正常任务。
- 身份暂未确认、EA 页面、启动和退出失败等可恢复环境错误，与未知程序崩溃分别计数。账号已安全清理且租约已关闭时，在同一进程中按 30/60/120/240/300 秒退避再试。清理尚未结束或领号前预检失败时，以专用退出码交给启动器冷却重试，保留原租约并优先恢复，不消耗版本崩溃次数。启动器的冷却时间跨重启保存；成功完成账号清除连续失败次数。
- 同一提交的未知异常退出或真正无响应恢复最多自动重试三次，达到上限后等待修复并继续检查新提交。验证码、人工停止、未确认的租约和报告证据问题仍遵循原有保护。
- 持有完整租约的游戏退出超时，以及尚未开始游玩时的 EA 清理失败，也进入保留原租约的冷却重试。每次重新确认进程已退出、EA 已退出登录后才关闭旧租约并领取下一账号；游玩后的输入释放未确认不按此规则放行。
- 新提交带来新的尝试机会；安装失败期间仍检查后续修复提交，不被一个坏提交永久锁住。
- 用户 F8/主动停止必须保持停止。后台可以继续更新，但不能自动开始账号。再次双击日常启动入口表示用户要求继续；登录自动启动保留停止意图。
- 原目录更新失败时可能需要后续修复提交。Git 工作区有已跟踪文件改动、分支分叉或本地提交时，不 reset、不丢弃改动，保持可诊断状态。
- 游戏更新、验证码、显示环境或凭据失效等实际环境问题仍需相应人工处置，推代码不能替代这些操作。修好环境后可显式继续。

## 本机状态和首次接入

EA 身份确认保留原匹配和置信度门槛。只有已登录页面连续三次读到同一个可信的其他账号，才报告 `IDENTITY_MISMATCH`；低置信度、不同读数和加载页面不累计成错误身份。超时仍无法确认时报告 `IDENTITY_UNCONFIRMED`，不会进入游戏。登录过渡画面缺少 BACK 时短暂重新取帧，仍不猜坐标或复用其他账号的验证码。现有文件登记进入可识别的下载管理器校验过程后，等待完成而非在 45 秒过渡超时后立即重启 EA。

EA 窗口识别先恢复最小化或隐藏的 EA 主窗口，再检查尺寸和页面。找不到可见窗口不代表账号已退出。EA 顶部出现应用更新/需要重启提示时，仅在 Apex 进程已退出的边界使用明确的 Restart app 链接；链接未独立识别时使用现有 Help → Restart app。重启后重新识别页面，并继续原退出登录流程，不能把重启成功当成退出登录成功。更新提示持续存在时停止重复重启并保留租约；正在游戏时延后 EA 重启。

私密配置、`windows/runs`、checkpoint 和报告 outbox 原位保留。`windows/runs/managed` 保存启动器锁、更新状态、尝试次数、当前运行 SHA、目标 SHA 和会话绑定的进程间请求；不保存凭据。

状态区分安装成功与进程响应：`INSTALLED` 只确认依赖安装和导入检查，`WORKER_STARTING` 表示进程已创建，收到本次启动会话匹配的新鲜主循环心跳后才进入 `RUNNING`。Windows 虚拟环境的 `python.exe` 会再启动实际解释器，两者 PID 可以不同；启动器以每次生成的 UUID 绑定心跳，分别记录包装进程 `pid` 和实际解释器 `workerPid`，不能要求两者相等。控制台展示运行/安装/目标短提交号；本机状态还记录安装时间、最近远端检查时间、主循环心跳时间及业务阶段。心跳不是业务完成证明，固定的 `0.5.1` 也不是 Git 更新成功证明。

独立版本上报线程复用 Reporter Token，定时把启动器状态送往 Forge 的 `version-status` 接口。代码安装阻塞主线程时仍可上报。只发送最新快照，generation/sequence 防止旧会话覆盖新状态；上报失败不影响运行、更新和租约。GitHub Actions 在 main 推送后通知 Forge 最新发布版本；Forge 只展示对比结果，不控制更新。

依赖安装成功标记保存在对应 `.venv` 内；即使启动器保留旧的依赖哈希，重建环境后安装中断也必须重试 pip，不能直接跳过。

第一次需要在每台机器原有任务合适的边界手动更新一次，然后使用新的 `account-cycle.cmd`。未安装启动器的旧进程无法凭空接收自动更新。日常入口登记当前用户登录后启动；需要可用的交互桌面，不在 Windows 服务会话中玩游戏。

关闭启动器窗口等强制退出可能留下待恢复租约；重新启动时先恢复。不能保证断电期间操作继续，也不能在没有网络/桌面时继续游戏。启动器异常退出必须避免遗留两个同时发送输入的 Runner。

## 验证

自动化验证覆盖：正常账号边界、未知/已知卡住时更新、暂停/退出、丢失响应后恢复、同版本重试限额、新提交解锁、Git 断网/分叉/脏工作区、依赖安装失败续试、更新锁、过期会话请求、重复启动和保留 outbox。发布工作流还在 Windows 上创建真实虚拟环境，检查包装进程与实际解释器 PID 不同情况下的心跳、版本确认及账号边界交接；通过后才通知 Forge。Windows 真机仍需验证：进程强制结束、F8、登录启动、依赖安装以及修复后业务恢复。测试通过不代表真实机器已接入或更新成功。
